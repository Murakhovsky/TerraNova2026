# CUW-D · UX-07 — робочий простір цілей (#522)

Базова версія: `10fc649df6aafdca432ec329ebd737f6a4abd1ec` · незалежний потік.
Master Spec §12, §19, AC-01, AC-02, AC-14, AC-16.

## Бізнес-мета

Надати власнику можливість сформулювати вимірюваний бізнес-результат,
обрати джерело перевірки та контролювати погоджене виконання.

## Учасники

- Власник цілі — менеджер, який формує чернетку та пропонує план.
- Незалежний погоджувач — інша уповноважена особа.
- Домен-власник — постачає спостереження й виконує дозволені дії.
- Platform Workflow — канонічне виконання та квитанції.

## Карта коду

- `symfony/src/Web/Federation/GoalsWorkspaceController.php` — SSR і захищені форми.
- `symfony/src/Web/Federation/GoalMetricPresentation.php` — відображення показників.
- `symfony/templates/experience/federation/goals.html.twig` — робочий простір.

## Повторне використання та адаптація

- **Повторне використання:** WorkspaceShellFactory, наявні перевірки прав менеджера й CSRF,
  FederationExperiencePreferenceStore, GoalSpecification, FederationGoalStore,
  FederationSmallGoalPlanProposalService, FederationDiscoveryPlanProposalService,
  FederationPlanApprovalCoordinator, FederationCanonicalWorkflowBridge,
  FederationTrustedOutcomeEvidenceResolver та джерела доменів.
- **Адаптація:** наявний SSR-контролер цілей; додано відображення строку
  та незмінних залежностей і ризиків плану. Без змін таблиць, маршрутів,
  налаштування DI, політик, агентів та виконавчої інфраструктури.
- **Нове:** GoalMetricPresentation — метадані відображення, а не другий реєстр;
  семантичний вибір показника, історична базова лінія за 30 днів із того самого
  джерела evidence, перевірка дати, обмежений вибір реальних угод та
  захист від повторного створення чернетки.

## Сценарій користувача (R5)

1. Опишіть результат звичайною мовою; явно оберіть показник, цільове значення
   і бажану дату. Історичне вимірювання не означає прогрес цілі.
   Нуль є допустимим лише за наявності підтвердженого спостереження.
2. Збережіть канонічну чернетку. Ця операція та її повторення не запускають Action.
3. Для пілоту оберіть **Створені завдання CRM**, ціль 1–3 та реальні угоди Sales
   для 1–3 кроків плану. Golden 50 використовує наявний Discovery-план
   з активним джерелом Growth Universe для Sales та фіксованою ціллю 50.
4. Перегляньте план, ризики й незалежне погодження. Запуск можливий тільки після
   завершеної квитанції Approval та активації канонічного виконання для організації.
   Наявний runtime повторно перевіряє політику й допуск виконавця.
5. Продовжуйте Workflow, спостерігайте прогрес і явно оцінюйте завершений
   Run за довіреними фактами домену. Режими Result/Process/Expert показують
   ту саму ціль і блокери з різною деталізацією.

## Межі реалізації

- Каталог обмежений 10 наявними критеріями попереднього Goals UI.
  Шість часових показників використовують зареєстровані джерела; три
  показники конкретного запуску не мають загальної базової лінії; Golden 50
  перевіряється наявним міждоменним агрегатом. Для інших збережених
  критеріїв точний ідентифікатор відображається в Expert.
- Пілот Sales використовує канонічний обмежений запит на отримання до 200 угод.
  Реальне джерело локальних завдань: `SalesLocalTaskOutcomeEvidenceProvider`
  → `MysqlSalesLocalTaskOutcomeReadModel`; шлях дії:
  `sales.create_task` → `CreateFollowupTaskHandler` → CRM.
  Наявність контракту не доводить доступність провайдера, політики, виконавця
  чи доставку результату.
- Канонічна специфікація вже має строк виконання. UI зберігає бажану календарну
  дату за Києвом; **не** змінює вікно evidence, автоматичне планування,
  SLA чи семантику оцінювання Run. Для цього потрібен окремий Kernel ADR.
- Чернетку створює людина без Hermes; довільний текст не може автоматично
  обрати невідомий критерій або змінити стан.
- Спільні навігація, переклади, адаптація UX-04 та інтеграція UX-05 належать
  визначеному інтегратору. Наявний маршрут використовує WorkspaceShell.
- Без зовнішнього виконання, production deployment, активації та merge.

## Матриця приймання

| Критерій | Перевірка |
| --- | --- |
| AC-01 / AC-02 права та ізоляція | Наявні перевірки прав та CSRF, запит Sales з контекстом, ізоляція tenant у тесті |
| AC-14 показники та evidence | `tests/unit/cuw_goal_metric_presentation.php`: реальний провайдер із тестовим портом читання, нуль, відсутнє джерело, помилка, строк |
| AC-16 один стан у режимах | Наявний браузерний сценарій R3/S4, бізнес-назва в Result/Process, точний контракт в Expert |
| Чернетка, відсутній CSRF, невідомий показник, повтор | `tests/browser/ux00_r1_r2_r3.mjs`: одна чернетка, жодної Action/Run, збережена дата |
| Мобільність та доступність | 390×844, знімок і axe у браузерному тесті; виконання очікується |
| Оцінка та відновлення | Federation persistence smoke перевіряє SSR-блок, оцінку та квитанції |

Потрібні `bash bin/verify fast`, Symfony lint/container/Twig, Runtime,
Frontend, браузерне приймання, Documentation та L2 на інтегрованому коді.
Реальний R5 Sales вимагає авторизованого менеджера, незалежного погоджувача,
активного домену, допущеного виконавця та підтвердженого джерела evidence.
Тестові дані та зелений CI не є живим бізнес-прийманням.

Відкат: revert PR; канонічні Goal, Plan, Run, Action та evidence залишаються
незмінними. Попередні чернетки читаються, а строк зберігається у вже наявному
полі специфікації.
