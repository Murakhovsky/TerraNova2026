# Архітектура COS

Ця сторінка дає технічну карту системи перед зануренням у класи, контракти та окремі домени.

## Головна ідея

COS розділяє **бізнес-смисл** і **механізми виконання**.

Домен знає, що означають клієнт, угода, об'єкт, діагностика або інша предметна сутність. Ядро не повинно знати ці деталі. Воно надає загальні механізми: виконання дій, події, правила, політики, черги, розширення, контекст і спостереження.

Це дозволяє додавати нові бізнес-напрями без перетворення ядра на колекцію винятків.

## Основні шари

У спрощеному вигляді система має такі рівні:

1. **Інтерфейси** приймають HTTP-запити, команди, повідомлення або дії користувача.
2. **Application layer** координує use cases і несе контекст організації та користувача.
3. **Domains** володіють бізнес-словником, станами, правилами і дозволеними переходами.
4. **Kernel** надає універсальні механізми виконання, подій, політик, автоматизації та агентів.
5. **Infrastructure** реалізує базу даних, черги, зовнішні API, файлові сховища та інші технічні адаптери.

Напрям залежностей має йти до контрактів і бізнес-смислу, а не навпаки.

## Межі відповідальності

Новий код спочатку повинен отримати власника.

Якщо поведінка має конкретний бізнес-смисл, вона належить домену. Якщо механізм однаково потрібен багатьом доменам і не містить їхньої термінології, він може належати Kernel або Platform.

Shared code не повинен ставати місцем, куди складають усе, для чого не захотіли визначити власника.

## Виконання

Типовий шлях виглядає так:

~~~text
вхід
  ↓
контекст tenant + identity
  ↓
application use case
  ↓
domain rule / state change
  ↓
event або action
  ↓
policy / approval / execution
  ↓
persistence + audit + observability
~~~

Критичні побічні ефекти не повинні губитися між зміною стану та зовнішнім викликом. Для цього COS використовує контрольовані lifecycle, durable outbox та повторюване виконання там, де це потрібно.

## Ізоляція організацій (multi-tenancy)

Організація є частиною контексту виконання, а не фільтром, який програміст має згадати додати в кінці SQL-запиту.

Tenant isolation має зберігатися в командах, репозиторіях, подіях, background workers та інтеграціях.

## Джерело правди

Пріоритет доказів такий:

~~~text
поточний код + активні тести
        ↓
manifests / process declarations
        ↓
generated reference
        ↓
narrative documentation
        ↓
ADR
~~~

Наратив пояснює систему, але не має суперечити executable source.
