# Мова та аудиторії документації

COS має **одну систему знань і три способи її пояснення**. Рівень деталізації визначається не тим, у якій папці лежить код, а тим, хто читає сторінку і яке рішення ця людина має прийняти після читання.

## Три аудиторії

### 1. Бізнес, клієнти та партнери

Мета: зрозуміти, що таке COS, яку проблему він вирішує, де дає користь і як виглядає впровадження.

Критерій якості простий: **текст має бути зрозумілим розумній дванадцятирічній дитині**.

Правила:

- короткі речення і невеликі абзаци;
- одна думка на абзац;
- спочатку проблема, приклад і користь;
- без назв класів, таблиць бази даних і внутрішніх механізмів;
- скорочення пояснюються, якщо вони не є загальновідомими;
- технічний термін використовується лише тоді, коли без нього втрачається зміст.

Кожна сторінка має відповідати на практичні питання: **що це, навіщо це потрібно, як це працює на простому прикладі і що отримує компанія**.

Поточний корпус: `for-business/`.

### 2. Інтегратор, керівник впровадження або менеджер компанії

Мета: дати людині робочу інструкцію, за якою COS можна підготувати, налаштувати, перевірити та запустити в реальній компанії.

Основний формат:

```text
Мета
→ Передумови
→ Конкретні дії
→ Очікуваний результат
→ Як перевірити
→ Типові проблеми
```

Тут дозволена професійна термінологія, але кожен важливий термін пояснюється нормальною мовою при першому використанні.

Поточний корпус: `for-integrators/`.

### 3. Розробники

Мета: дати достатньо точну технічну модель, щоб новий програміст міг зрозуміти межі системи, безпечно внести зміни й довести їх тестами.

Технічна сторінка має відповідати щонайменше на такі питання:

- для чого існує цей компонент;
- яким контрактом він володіє;
- які дані та стани проходять через нього;
- від чого він залежить;
- що відбувається при помилці;
- які правила безпеки та ізоляції діють;
- як поведінка перевіряється;
- де шукати точне джерело правди в коді або згенерованому довіднику.

Поточний вхід: `for-developers/`. Детальний український технічний корпус залишається в `00-start` – `12-reference`.

## Одна семантика, різна глибина

Три рівні не повинні створювати три різні версії COS.

Наприклад, одна й та сама дія пояснюється так:

- **бізнес:** COS може створити задачу, надіслати повідомлення або виконати іншу дозволену дію;
- **впровадження:** для кожної дії визначаються умови запуску, рівень автоматизації та потреба в підтвердженні людиною;
- **розробка:** Action є виконуваною операцією з tenant-власністю, життєвим циклом, ідемпотентністю, політикою виконання та контрольованим завершенням.

Змінюється глибина пояснення, а не сутність системи.

## Локалі

Українська та англійська є повноцінними локалями документації для трьох основних аудиторій.

Структура локалей визначається централізовано у:

```text
docs/.vitepress/locales.mjs
```

Українська локаль залишається в корені `docs/`, щоб не ламати чинні адреси. Англійська живе в `docs/en/`.

Наступні мови додаються окремими префіксами:

```text
docs/pl/
docs/de/
docs/es/
...
```

Для додавання нової мови потрібно:

1. додати локаль у `LOCALES`;
2. перекласти ті самі семантичні сторінки для трьох аудиторій;
3. не змінювати назви semantic routes без окремої міграції;
4. запустити `npm run docs:check`;
5. перевірити збірку `npm run docs:build`.

`check-audience-locales.mjs` не дозволяє зареєструвати мову, у якій відсутня частина обов'язкового каркаса.

## Переклад не є калькою

Локалізації мають передавати однаковий зміст природною мовою.

Поганий підхід: буквально копіювати порядок слів та конструкції іншої мови.

Правильний підхід: зберігати поняття, факти, обмеження та посилання, але формулювати їх так, як це природно для читача відповідної мови.

## Перемикач мови

Якщо еквівалент сторінки існує, перемикач веде на нього.

Якщо глибокий технічний матеріал ще не перекладений, перемикач веде на найближчий вхід для тієї самої аудиторії, а не на неіснуючу сторінку.

Це правило реалізоване через locale registry, а не через окремий набір умов для кожної мови.

## Автоматичні перевірки

`npm run docs:check` перевіряє:

- мовну чистоту української публічної документації;
- повноту обов'язкових сторінок для кожної зареєстрованої локалі;
- внутрішні посилання;
- frontmatter та документаційні контракти;
- відповідність доменів і версій executable source;
- процеси, coverage та інші чинні documentation gates.

## Правило для нової сторінки

Перед написанням автор визначає:

1. аудиторію;
2. локаль;
3. практичне питання читача;
4. потрібний рівень технічної глибини;
5. джерело правди;
6. куди вести читача за наступним рівнем деталей.

Сторінка, яка одночасно намагається продавати продукт, навчати інтегратора і документувати клас, має бути розділена. Навіть документація заслуговує знати, для кого вона прокинулась цього ранку.
