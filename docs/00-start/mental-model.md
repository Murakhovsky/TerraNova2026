# Ментальна модель COS

COS найпростіше розуміти не через класи, а через **ланцюг відповідальності**: хто володіє бізнес-смислом, хто приймає рішення, хто дозволяє дію і хто її виконує.

## Два основні шляхи виконання

### Прямий варіант використання (direct use case)

```text
Користувач / інтерфейс
    ↓
Варіант використання / команда
    ↓
Перевірка домену
    ↓
Зміна стану
    ↓
Подія + результат
```

### Автоматизація за подією (event-driven automation)

```text
Бізнес-подія
    ↓
Правило / агент
    ↓
Пропозиція дії
    ↓
Політика
    ↓
Погодження / автоматично / заборонено
    ↓
Виконання
    ↓
Подія результату + аудит
```

Не кожна операція потребує агента, черги або погодження. COS не повинен перетворювати просте оновлення на релігійний ритуал із сімнадцяти мікросервісів.

## 1. Намір або бізнес-операція

На початку є конкретна бізнес-мета: створити звернення, змінити етап, почати діагностичну сесію, прийняти об’єкт нерухомості або виконати іншу операцію домену.

Інтерфейс лише передає намір до рівня застосунку.

## 2. Варіант використання або команда

Рівень застосунку оркеструє змістовну операцію:

```text
Вхідні дані
→ перевірка та контекст
→ логіка домену / застосунку
→ збереження / порти взаємодії
→ результат
```

Команда (command) є запитом щось зробити. Подія (event) є фактом, що щось уже сталося. Плутати їх зручно лише до першої серйозної автоматизації.

## 3. Володіння домену

Домен (domain) визначає:

- словник понять;
- інваріанти;
- переходи станів;
- бізнес-події;
- контракти взаємодії;
- повноваження над власними даними.

Ядро не вирішує, чи звернення кваліфіковане. Вебконтролер не вирішує, чи валідна методологія діагностики. Інфраструктура не визначає, що означає модерація об’єкта нерухомості.

## 4. Подія

Подія описує факт. Наприклад:

```text
sales.call.completed
```

означає «дзвінок завершився», а не «надішли наступне повідомлення».

Коли подія запускає подальшу обробку, зміна бізнес-стану, подія та вихідна черга (Outbox) мають бути узгоджені в межах однієї транзакції.

## 5. Надійна доставка

```text
Фіксація в базі даних
   ↓
Вихідна черга (Outbox)
   ↓
Споживач / робітник
```

Доставка може гарантувати щонайменше одну спробу (at-least-once), тому побічні ефекти повинні бути ідемпотентними, тобто безпечними при повторному виконанні.

## 6. Рішення

Після події рішення може приймати правило або агент.

**Правило (rule)** використовує детерміновану логіку. **Агент (agent)** використовує мовну модель та контекст, яким володіє домен.

Агент повертає пропозицію. Він не отримує право змінювати систему лише тому, що вміє генерувати переконливий JSON.

## 7. Пропозиція дії

Рішення матеріалізується як контрольована дія (Action) або пропозиція дії (ActionProposal), наприклад:

```text
sales.send_followup
sales.update_deal
integration.sync_contact
```

## 8. Політика повноважень

Дія проходить перевірку політикою (policy):

```text
Дія
  ↓
Політика
  ├─ AUTO                 автоматичне виконання
  ├─ APPROVAL_REQUIRED    потрібне погодження
  └─ DENIED               заборонено
```

Безпечним базовим правилом для зміни стану залишається «заборонено, доки явно не дозволено» (default deny).

## 9. Погодження

Якщо потрібне рішення людини, створюється окремий життєвий цикл погодження (approval lifecycle).

Агент не затверджує власне рішення. Люди іноді теж не повинні, але для них ми поки не написали ядро.

## 10. Черга та виконання

Надійна черга використовується там, де потрібне асинхронне виконання, повторні спроби, оренда задачі робітником або окремий стан невиправної помилки.

Виконавець знаходить обробник, яким володіє домен, через реєстр середовища виконання та модуля, а потім викликає вихідні порти й адаптери.

## 11. Результат

Ядро може завершувати універсальні події життєвого циклу виконання, а домен створює власні бізнес-події, коли змінено бізнес-стан.

Ядро не вигадує бізнес-семантику замість домену.

## 12. Аудит і спостережуваність

Після виконання система повинна дозволяти відповісти:

- що сталося;
- який домен володів операцією;
- який контекст використано;
- яке правило або агент прийняли рішення;
- яку дію запропоновано;
- яка політика спрацювала;
- чи було погодження;
- який обробник виконав зміну;
- який зовнішній виклик відбувся;
- який результат отримано;
- де сталася помилка.

## Ментальна формула

```text
НАМІР
 → ОПЕРАЦІЯ ДОМЕНУ
 → ФАКТ
 → РІШЕННЯ
 → ПРОПОЗИЦІЯ
 → ПОВНОВАЖЕННЯ
 → ВИКОНАННЯ
 → РЕЗУЛЬТАТ
 → ПОЯСНЕННЯ
```

## Рівні системи

```text
Бізнес
  ↓
Бізнес-процес (workflow)
  ↓
Домен
  ↓
Варіант використання / команда / подія
  ↓
Середовище виконання ядра (Kernel Runtime)
  ↓
Політика / погодження / черга
  ↓
Порт домену
  ↓
Інфраструктурний адаптер
  ↓
Зовнішня система / база даних
```

## Модель джерела правди

Для документації та коду діє один принцип:

```text
поточний main
├─ код
├─ тести
├─ декларації модулів і контрактів
├─ документація
└─ згенерований технічний довідник
```

Твердження про поточний стан мають підтверджуватися тим самим комітом `main`. Цільовий стан не видається за вже реалізовану поведінку.

## Сім питань для налагодження

1. Який бізнес-намір або факт ми обробляємо?
2. Який домен ним володіє?
3. Який варіант використання, команда або подія представляє операцію?
4. Де приймається рішення: у логіці домену, правилі чи агенті?
5. Яка дія або зміна стану виконується?
6. Яка політика повноважень дозволила її?
7. Де записані результат, подія та аудит?

Якщо немає чітких відповідей, проблема зазвичай не в ШІ. Причинно-наслідкова траса просто ще не сформована.
