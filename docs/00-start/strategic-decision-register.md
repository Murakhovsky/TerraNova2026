# Реєстр стратегічних рішень COS

**COS Strategic Decision Register — версія 0.1 (Founding Draft)**  
**Дата:** 22 жовтня 2026 року  
**Статус:** початковий реєстр пропозицій; затвердження потребує окремого рішення

**Підстава:** [Стратегічна хартія COS](./strategic-charter.md) · [Стратегічна дорожня карта COS](./strategic-roadmap.md)

## 1. Призначення та межі

Це журнал **чому** COS обирає певний довгостроковий напрям, **хто і на якій підставі** погодив вибір та **що може його змінити**.

Реєстр не дублює:

- технічні [Architecture Decision Records (ADR)](../11-decisions/README.md), що пояснюють конкретні інженерні інваріанти;
- backlog, ТЗ і Pull Request, які описують реалізацію;
- [поточний стан продукту](../01-product/current-scope.md) і виконувані докази AS-IS.

Принцип ієрархії: **Хартія → стратегічне рішення → Roadmap → ADR / ТЗ / робочий пакет → перевірений результат**. За суперечності між бажаним стратегічним напрямом і кодом останній залишається правдою про фактичну реалізацію; прогалину оформлюють як зміну, а не приховують.

## 2. Життєвий цикл та правила управління

| Статус | Значення |
| --- | --- |
| **Proposed** | Рішення сформульовано, але ще не затверджено |
| **Accepted** | Уповноважений власник стратегії явно ухвалив рішення; запис містить дату та посилання |
| **Deferred** | Рішення відкладено; визначено умову повернення |
| **Rejected** | Альтернатива розглянута й відхилена з поясненням |
| **Superseded** | Існує нове рішення із посиланням на цей запис і причиною заміни |

**Правила:**

1. Формат ID: SDR-0001, SDR-0002 тощо. Номер ніколи не перевикористовується.
2. Пропозицію може подати учасник проєкту; **Accepted** ставить тільки визначений власник стратегічного рішення. До явного затвердження засновником усі наведені нижче записи — **Proposed**.
3. Запис має визначати проблему, мінімум дві альтернативи (включно зі збереженням поточного стану, де доречно), наслідки, ризики, очікувану бізнес-цінність, тригер перегляду та посилання на докази.
4. Стратегічне рішення, яке змінює інваріант чи технічний контракт, потребує **окремого ADR**; один SDR сам собою не санкціонує небезпечну зміну.
5. Суттєву зміну ухваленого рішення оформлюють новим SDR зі зв'язком **supersedes / superseded by**, а не стирають старе обґрунтування. Git зберігає історію правок і рішень.
6. Запропоновані винятки з Хартії містять строк, власника, ризики, механізм повернення та формальне погодження. **Tenant isolation, authorization, anti-duplicate execution і critical audit не допускають спрощення через waiver.**

### Шість питань перед затвердженням

Застосувати критерії розділу VIII [Хартії](./strategic-charter.md): вимірюваний outcome, vendor neutrality, integratе-before-rebuild, збереження execution authority, співвідношення вартості/ризику/часу та шлях до клієнтів або доходу. Кожне «ні» потребує явного trade-off, а не замовчування.

## 4. Записи рішень

### SDR-0001: Позиціонування Business Operating System

- **Статус:** Proposed. **Дата пропозиції:** 2026-10-22. **Пропонований власник рішення:** засновник COS; формальне погодження відсутнє.
- **Питання:** який рівень цінності та відповідальності має займати COS відносно CRM, ERP та агентних платформ?
- **Альтернативи:** (A) універсальна агентна платформа; (B) монолітна ERP/CRM із вбудованим AI; (C) незалежний **Business Operating System** над чинними системами, з Goal-to-Outcome governance.
- **Пропозиція:** обрати (C). Ключова цінність — координація ресурсів, людей, систем та AI навколо вимірюваних бізнес-цілей.
- **Обґрунтування:** менша вимога міграції, ширший integration surface та власний контроль економічних результатів.
- **Trade-off / ризик:** складність міжсистемних контрактів і доказу outcome; нечітке позиціонування без конкретних успішних сценаріїв.
- **Очікуваний доказ:** повторювані пілотні Goal-to-Outcome сценарії з незалежною оцінкою результату й зрозумілою економічною цінністю.
- **Тригер перегляду:** пілоти не підтверджують міжсистемної цінності або economics впровадження є неприйнятними.
- **Зв'язок:** [Хартія](./strategic-charter.md), [Roadmap](./strategic-roadmap.md). **Затвердження:** очікується.

### SDR-0002: Інтегрувати агентні рушії замість перебудови

- **Статус:** Proposed. **Дата пропозиції:** 2026-10-22. **Пропонований власник:** засновник COS; затвердження відсутнє.
- **Питання:** чи будувати власний універсальний agent runtime, чи інтегрувати наявні рішення?
- **Альтернативи:** (A) власний повний planning/runtime stack; (B) жорстка залежність від одного постачальника; (C) **контракт Agent Provider + Gateway + змінні адаптери**.
- **Пропозиція:** (C), з обмеженою власною розробкою там, де COS володіє стратегічними інваріантами, а не планувальником агента.
- **Обґрунтування:** швидше використання інновацій, менший vendor lock-in і витрати на підтримку сторонніх агентних алгоритмів.
- **Trade-off / ризик:** зовнішні API та ліцензії нестабільні; потрібні fallback, versioning, security та операційна спостережуваність.
- **Очікуваний доказ:** один бізнес-сценарій працює з двома відмінними провайдерами без зміни бізнес-правил і без обхідної mutation authority.
- **Тригер перегляду:** порушення security/portability, неприйнятна сукупна вартість адаптерів або поява незамінної бізнес-потреби в обмеженому власному runtime.
- **Зв'язок:** [Roadmap, етап 2](./strategic-roadmap.md), [ADR-0015](../11-decisions/ADR-0015-cos-federation-architecture.md). **Затвердження:** очікується.

### SDR-0003: Єдине підконтрольне виконання

- **Статус:** Proposed на стратегічному рівні. **Дата пропозиції:** 2026-10-22. **Пропонований власник:** засновник COS; затвердження SDR відсутнє.
- **Питання:** чи дозволяти зовнішнім агентам, Federation або UI створювати незалежні mutation і Run/Step execution paths?
- **Альтернативи:** (A) власний executor для кожної вертикалі; (B) агент виконує критичні записи напряму; (C) **один Platform Workflow та чинні Policy/Approval/Action/Domain boundaries**.
- **Пропозиція:** (C). Goal Management володіє Goal/Plan/OutcomeEvaluation, але не створює другий загальний executor.
- **Обґрунтування:** запобігання дублям, збереження прав, доказовості, rollback і domain ownership.
- **Trade-off / ризик:** інтеграції складніші; потрібні receipts, revalidation і reconciliation для зовнішніх ефектів.
- **Очікуваний доказ:** Golden 50, single-writer authority audit, failover, operator acceptance.
- **Тригер перегляду:** лише документоване технічне обмеження, що не знижує безпеку та потребує відповідного ADR.
- **Зв'язок:** чинний **[прийнятий ADR-0015](../11-decisions/ADR-0015-cos-federation-architecture.md)** та [нормативне ТЗ](../03-architecture/cos-federated-architecture-implementation-spec.md). Статус **Accepted** цього ADR **не означає** автоматичного затвердження цього SDR. **Затвердження SDR:** очікується.

### SDR-0004: Послідовність інвестицій у розробку

- **Статус:** Proposed. **Дата пропозиції:** 2026-10-22. **Пропонований власник:** засновник COS; затвердження відсутнє.
- **Питання:** які спроможності фінансувати і доводити першими за обмежених ресурсів?
- **Альтернативи:** (A) паралельно будувати всі домени; (B) спершу marketplace/agent framework; (C) **Reliable Core → Open Agent Ecosystem → Business Intelligence → Enterprise Ecosystem** із evidence gates.
- **Пропозиція:** (C). Досліджувати майбутні етапи можна раніше, але запуск не обходить попередній gate.
- **Обґрунтування:** концентрація ресурсів, зменшення ризику архітектурних дублювань та першочергове підтвердження business outcomes.
- **Trade-off / ризик:** повільніший вихід другорядних функцій; ризик надмірного перфекціонізму ядра без продажів.
- **Очікуваний доказ:** формальні Gate 1–4 та прив'язка пакетів до конкретних issue/PR/evidence; комерційна перевірка паралельно.
- **Тригер перегляду:** нова перевірена ринкова можливість, суттєвий технічний ризик або невідповідність ефекту витратам.
- **Зв'язок:** [Roadmap](./strategic-roadmap.md). **Затвердження:** очікується.

### SDR-0005: Паралельна комерційна перевірка

- **Статус:** Proposed. **Дата пропозиції:** 2026-10-22. **Пропонований власник:** засновник COS; затвердження відсутнє.
- **Питання:** коли починати доводити попит та перевіряти монетизацію COS?
- **Альтернативи:** (A) після завершення всіх технічних етапів; (B) продавати необмежені обіцянки до перевірок; (C) **обмежені пілоти й оцінка economics уже разом із Reliable Core**, без порушення security gates.
- **Пропозиція:** (C). Вибрати реальні задачі, зняти baseline, погодити критерії успіху, порахувати собівартість інтеграції та готовність платити.
- **Обґрунтування:** відфільтровувати технічно цікаві, але комерційно непотрібні напрями до великого інвестування.
- **Trade-off / ризик:** ранні клієнтські запити можуть тягнути до кастомізації; потрібен контроль product scope і явні межі pilot.
- **Очікуваний доказ:** порівнювана метрика до/після та documented willingness-to-pay / total cost для конкретного сценарію.
- **Тригер перегляду:** недостатня доказовість або неприйнятні операційні ризики пілоту.
- **Зв'язок:** [Roadmap, комерційний потік](./strategic-roadmap.md). **Затвердження:** очікується.

## 5. Шаблон нового стратегічного рішення

При додаванні нового рішення створіть запис з наступними полями (без заповнення вигаданими фактами):

| Поле | Вимога |
| --- | --- |
| ID / тема | Наступний вільний SDR-номер і конкретне питання |
| Статус / дата | Proposed до явного approval; дати пропозиції та рішення окремо |
| Ініціатор / власник | Хто пропонує та хто уповноважений прийняти |
| Контекст | Проблема, scope, залежності та наявні факти з посиланнями |
| Альтернативи | Щонайменше два реальні варіанти, включно з причиною відмови |
| Рішення | Однозначне формулювання; принцип чи заборона, що змінюються |
| Бізнес-цінність | Очікуваний outcome, клієнтський ефект, витрати й спосіб вимірювання |
| Ризики й наслідки | Vendor, security, legal, cost, architecture, operations |
| Критерії перевірки | Яке evidence доведе або спростує гіпотезу |
| Залежності / артефакти | ADR, Roadmap, issue, PR, acceptance logs, market evidence |
| Тригер перегляду | Конкретна подія чи метрика, за якої рішення відкривається знову |
| Approval | Хто і коли погодив, посилання на схвалений PR/запис |
| Supersedes / superseded by | Історія заміни без стирання попередньої аргументації |

## 6. Ритуал перегляду та дисципліна змін

- **На кожну значну ініціативу:** перевірити її проти Хартії, актуальних SDR і доказів Roadmap перед створенням великого пакета розробки.
- **На Gate / після пілоту / при зміні ризику:** переглянути пов'язані SDR, але не переписувати історію без нового рішення.
- **На зміну Хартії:** оцінити всі Accepted SDR і відповідні ADR та пояснити, які треба supersede чи адаптувати.
- **Під час підготовки PR:** додати посилання на відповідний SDR або аргументувати, чому нове стратегічне рішення не потрібне.

Прийняте стратегічне рішення може бути неправильним. Некеровано змінене рішення, про причину якого ніхто не пам'ятає, майже гарантовано виявиться дорожчим.
