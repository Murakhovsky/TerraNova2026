# Стратегічна дорожня карта COS

**COS Strategic Roadmap — версія 0.1 (Founding Draft)**  
**Дата:** 22 жовтня 2026 року  
**Статус:** проєкт для стратегічного затвердження  
**Підстава:** [Стратегічна хартія COS](./strategic-charter.md)

> **Build the Business OS. Integrate the Agents. Own the Outcomes.**

## 1. Мета та правила цієї карти

Мета Roadmap — переводити стратегічні принципи COS у **послідовність перевірюваних бізнес-результатів**, а не накопичувати довільні модулі та агентні рушії.

Це **цільовий план (TO-BE)**, не звіт про виконання (AS-IS) і не набір обіцяних дат. Етап завершується лише після перевірки доказів готовності. Фактичні функції, версії та технічний стан мають підтверджуватися [поточним станом COS](../01-product/current-scope.md), кодом, перевірками та операторськими доказами.

Вся розробка йде двома взаємозалежними потоками:

- **Product & Reliability:** правильне виконання, підтверджені результати, сумісність, безпека та витрати.
- **Customer & Revenue:** реальні сценарії клієнтів, вимірювання економічного ефекту, пілотні впровадження, продажі та повторюваний дохід.

Комерційну перевірку не слід відкладати до завершення всіх чотирьох технічних етапів. Жодна технічна демонстрація сама по собі не підтверджує ринковий попит.

## 2. Початковий стан і стратегічні обмеження

Станом на дату проєкту Roadmap у COS уже існують частини Goals, Federation, Platform Workflow, Action/Policy/Approval і бізнес-домени. **Це не означає прийняття всіх критеріїв промислової готовності.** Зокрема, сам факт наявності коду чи зеленого unit-тесту не доводить Golden 50 або незалежного бізнес-результату.

Базові технічні джерела:

- [Нормативне ТЗ федеративної архітектури](../03-architecture/cos-federated-architecture-implementation-spec.md).
- [Операторський сценарій Goals і Golden 50](../02-workflows/federation-goals-small-scenarios-operator.md).
- [ADR-0015: федеративна архітектура](../11-decisions/ADR-0015-cos-federation-architecture.md).
- [Поточний стан продукту](../01-product/current-scope.md).

**Незмінні обмеження на всіх етапах:** один canonical writer для Run/Step і критичної бізнес-операції; ніякого прихованого обхідного виконання агентом; Domain володіє бізнес-правдою; tenant/permissions/policy/approval є обов'язковими; повтор не породжує другого зовнішнього ефекту; результат Goal підтверджує незалежне джерело бізнес-фактів. Ці правила не можна послаблювати заради швидшого демо.

## 3. Карта етапів

| Етап | Основний результат | Залежність для переходу |
| --- | --- | --- |
| **1. Reliable Core** | Надійне міждоменне виконання Goal і незалежно перевірений Outcome; перші доказові пілоти | Пройдено технічні та операторські критерії Gate 1 |
| **2. Open Agent Ecosystem** | Зовнішні агентні рушії та корпоративні системи підключаються через контрольовані адаптери без міграції бізнесу на новий runtime | Пройдено Gate 1 та Gate 2 |
| **3. Business Intelligence** | Дані про виконання перетворюються на пояснювані рекомендації та вимірюване покращення рішень | Пройдено Gate 2 та Gate 3 |
| **4. Enterprise Ecosystem** | Керована міжорганізаційна співпраця й партнерські розширення | Пройдено Gate 3 та Gate 4 |

Етапи описують **порядок розвитку capability**. Дослідження наступного етапу можливі паралельно, але не повинні обходити acceptance gate попереднього.

## 4. Етап 1: надійне ядро (Reliable Core)

**Ціль:** довести, що COS координує реальні бізнес-операції через один контрольований шлях і підтверджує їхній ефект, а не лише статус виконання.

### Пакети першочергової реалізації

| Пріоритет | Робочий пакет | Результат та доказ |
| --- | --- | --- |
| P0 | **Execution Authority Audit** | Один writer для кожного Run/Step; доведена відсутність подвійного dispatch, dual writes та обхідних mutation paths |
| P0 | **Golden 50 end-to-end** | 50 незалежних сценаріїв із реальними Growth Candidates → Sales Leads → Documents, коректною атрибуцією та окремо збереженою оцінкою Goal |
| P0 | **Recovery & Failover** | Crash, retry, timeout, неоднозначний зовнішній ефект і повторне доставлення не створюють дубльованих дій; є reconciliation та audit trail |
| P0 | **Production Acceptance** | MySQL, worker, tenant, permission, approval, deployment attestation, rollback і operator sign-off на визначеному середовищі |
| P1 | **Consolidation** | Перехідні Federation/Legacy executor-компоненти вилучені після parity, або збережені з власником, причиною та планом retirement |
| P1 | **Federated Domain Expansion** | Другий і наступні сценарії працюють через стандартні capability contracts без переписування універсального executor |
| P1 | **Experience Package B** | Result / Process / Expert спираються на спільні канонічні проєкції, а не на паралельні джерела фактів чи UI-дозволи |

P1 не є дозволом ігнорувати P0. Виняток — вузька робота P1, що прямо усуває блокування P0 і не відкриває нових неконтрольованих шляхів виконання.

### Контрольний рубіж 1: готовність ядра

Gate 1 можна позначити **пройденим** лише за наявності:

1. Трасувань із чіткими власниками Goal, approved Plan, Workflow Run/Step, Action receipt та Domain Outcome.
2. **П'ятдесяти незалежних, перевірених Golden 50 результатів**, а не п'ятдесяти синтетичних записів або одного агрегованого статусу «успішно»; збереженої окремої оцінки Goal.
3. Доказів, що повторні виклики, одночасні запуски та відновлення після збою не дублюють зовнішні бізнес-ефекти.
4. Тесту ізоляції tenant, повноважень, незалежного погодження, відкату й операторського контролю на цільовій конфігурації.
5. Переліку відкритих P0-дефектів із рішенням **block / explicit conditional acceptance**; security та authorization інваріанти не мають waiver.
6. Посилання на зафіксовану версію коду, середовище, dataset, run IDs, журнали перевірки й особу, яка прийняла результат.

**Успішний CI, статус Workflow Completed або намальований UI не замінюють Gate 1.**

## 5. Етап 2: відкрита екосистема агентів (Open Agent Ecosystem)

**Ціль:** використовувати наявні агентні технології клієнта та сторонні продукти як виконувані можливості COS, не створюючи ще одну конкуруючу універсальну агентну платформу.

### Пріоритетні можливості

1. **Agent Provider Contract:** версіоновані discovery/capabilities, invocation, input/output schemas, result receipts, cancellation, timeout, error classes, idempotency та trace/correlation identifiers.
2. **Agent Gateway:** tenant-scoped credentials, quotas, budgets, permissions, policy enforcement, observability та обмеження зовнішніх ефектів.
3. **Контрольований Action bridge:** агент може пропонувати дії й повертати результати; business mutations проходять лише через відповідні canonical Domain/Platform contracts, Policy/Approval і Platform Workflow.
4. **Адаптери до зовнішніх runtime:** Hermes, OpenClaw або інші провайдери є кандидатами для оцінки за функціями, безпекою, ліцензією, операційними витратами та стабільністю API. Жоден не є обов'язковою залежністю COS.
5. **Підключення чинного корпоративного ПЗ:** спершу вибіркові сценарії з наявними CRM/ERP/API клієнта, а не обов'язкова міграція даних.

**Не будувати на цьому етапі:** власні повноцінні planning/runtime frameworks, приватний agent dispatch path, провайдер-специфічну бізнес-логіку в Kernel або універсальний «розумний» executor без перевірених вимог.

### Контрольний рубіж 2: реальна переносимість

- Працюють щонайменше **два відмінні Agent Provider адаптери** з одним семантичним сценарієм та порівнюваними квитанціями; mock-only доказу недостатньо.
- Щонайменше одна інтеграція використовує **існуючу зовнішню бізнес-систему** і не вимагає переходу користувача на нову CRM.
- Зовнішній runtime не має неавторизованих записів у критичні бізнес-об'єкти; контролюються permission, approval, budget, revocation, replay, timeout та audit.
- Заміна провайдера не змінює бізнес-правила, семантику Goal і canonical Workflow.
- Задокументовано реальну вартість викликів, затримки, частоту помилок і дію відмови провайдера для погодженого пілотного сценарію.

## 6. Етап 3: бізнес-інтелект (Business Intelligence)

**Ціль:** перетворити execution evidence, корпоративні знання та історію рішень на покращення економічних результатів.

Пріоритет: джерела доказів та їх provenance → tenant-scoped knowledge/memory → пояснювана аналітика Goal/KPI/cost → рекомендації та next-best-action → контрольована перевірка результативності рекомендацій.

**Gate 3:** є аудит джерел знань, механізм актуалізації й видалення даних, захист tenant, виміряна якість рекомендацій, базова лінія порівняння й зафіксований економічний ефект щонайменше на одному реальному бізнес-сценарії. Рекомендація не стає дозволом на дію.

Не розробляти довільну «корпоративну пам'ять» без конкретних сценаріїв її корисності, вимог до конфіденційності й метрик.

## 7. Етап 4: екосистема підприємств (Enterprise Ecosystem)

**Ціль:** безпечна співпраця незалежних організацій через узгоджені бізнес-контракти, прозору відповідальність і вимірювання результатів.

Можливості: міжорганізаційні запити та делегування, scoped federation identity/permissions, контрактні дані, партнерські інтеграції, каталог можливостей і marketplace за підтвердженого попиту.

**Gate 4:** є щонайменше один реальний міжорганізаційний процес з погодженими правами, власниками даних, відповідальністю за збої, аудитом, процедурами відкликання доступу/вирішення спорів і позитивною вимірюваною бізнес-цінністю. Правові та договірні умови перевірені для ринку запуску.

Marketplace не є окремою самоціллю до появи повторюваної взаємодії учасників.

## 8. Комерційний потік через усі етапи

Паралельно з Reliable Core слід сформувати короткий реєстр цільових сегментів, 1–2 пріоритетних сценарії впровадження та критерії економічної цінності.

| Перевірка | Що фіксуємо |
| --- | --- |
| Попит | Хто приймає рішення, яку бізнес-проблему вирішуємо, чим користуються зараз |
| Початкова база | Вартість процесу, тривалість, обсяг, частота помилок, ручна праця до COS |
| Пілот | Обсяг доступу, строки, відповідальний з боку клієнта, приймальні критерії та ризики |
| Ефект | До/після: час, витрати, конверсія, виручка або інша погоджена метрика; невизначеність вимірювання |
| Монетизація | Готовність платити, модель регулярного платежу, витрати на підтримку та інтеграцію |
| Масштабованість | Чи можна повторити впровадження без індивідуального переписування ядра |

**Проміжний комерційний gate:** запуск нової продуктової вертикалі потребує хоча б перевіреної гіпотези покупця, проблеми, вимірюваного виграшу та вартості інтеграції. Дата чи кількість платних клієнтів не вигадуються: погоджені цільові значення виносяться до окремого операційного плану.

## 9. Правила пріоритетів, залежностей і змін

1. **P0 safety/correctness > новий функціонал.** Не запускати ширші autonomous use cases на недоведеному executor.
2. **Outcome > feature count.** Завдання без вимірюваного результату залишається гіпотезою, не закритим milestone.
3. **Integrate before rebuild.** Кожна нова агентна технологія проходить buy/adapt/build аналіз із сукупною вартістю володіння.
4. **Один власник рішення.** Для кожного активного пакета визначаються owner, issue/PR, критерій прийняття, залежності та evidence URL.
5. **Обмежити паралельність.** За дефіциту ресурсів вести один основний технічний P0-потік і один комерційний пілотний потік; масштабувати WIP лише за наявності відповідальних.
6. **Не змішувати Roadmap і реалізацію.** ТЗ, ADR, backlog, acceptance results та production evidence ведуться окремо й лінкуються до відповідного етапу.
7. **Перегляд — на подію.** Зміна ринку, агентних API, технічного інваріанта, витрат або результати пілоту можуть змінити пріоритет через [Реєстр стратегічних рішень](./strategic-decision-register.md).

## 10. Формат прийняття етапу

Для кожного Gate створюється запис про рішення з полями: номер Gate; дата; версія roadmap; scope й environment; критерії та прямі посилання на артефакти доказів; невирішені ризики; відповідальний; рішення **pass / conditional / fail**; обмеження conditional; наступний перегляд.

Стан кожного пакета ведеться окремо як **not started / in progress / blocked / verified / accepted**. Зміна статусу **accepted** допускається тільки після evidence та sign-off, а не за оцінкою відсотка готовності.

Перше завдання після затвердження Roadmap: зв'язати P0 Reliable Core із чинними GitHub issues, власниками, тестовим середовищем і фактичними доказами Golden 50. Доти перелік пакетів є **планом, а не заявою про виконання**.

---

**Основний орієнтир:** не кількість створених агентів, а кількість надійно досягнутих, підтверджених та економічно цінних бізнес-результатів.
