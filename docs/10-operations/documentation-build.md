# Збірка документації

Документація COS збирається з того самого `main` commit, що містить executable code. Generated reference також має бути закомічений у тому самому стані, а не існувати правильно лише всередині CI workspace.

## Канонічний ланцюжок

```text
main code / manifests / structured contracts
        ↓
reference generators
        ↓
docs/12-reference/*.md
        ↓
git drift gate
        ↓
reference + documentation validation
        ↓
VitePress 1.6.4
        ↓
public/docs
```

Cross-branch checkout, `.docs-source` і `COS_DOCS_SOURCE_ROOT` більше не є частиною canonical pipeline.

## Локальні команди

```bash
npm run docs:generate
git status --short -- docs/12-reference
git diff -- docs/12-reference
npm run docs:generate:check
npm run docs:check
npm run docs:build
npm run docs:dev
npm run docs:preview
```

Після `npm run docs:generate` зміни в `docs/12-reference` не є сміттям build process. Це сигнал, що executable/structured authority змінився і generated reference треба закомітити разом із відповідною зміною.

`docs:dev` і `docs:build` перед запуском VitePress можуть регенерувати reference для rendering, але це не скасовує committed-sync requirement у `main`.

## Generated reference

Канонічні generated pages включають, зокрема:

```text
application-use-cases.md
architecture-graph.md
business-processes.md
commands.md
configuration.md
database.md
errors-and-failures.md
event-types.md
extension-points.md
module-capabilities.md
module-routes.md
permissions-capabilities.md
cross-domain-process-topology.md
capability-debt.md
domain-process-coverage.md
```

Authority для них — current code/manifests або explicit structured documentation contracts, а не ручний Markdown.

## Drift gate

CI після generation перевіряє Git working tree для `docs/12-reference`.

Якщо generator змінив tracked file або створив новий generated file, build падає і показує:

- `git status --short` для generated reference;
- unified `git diff` для tracked changes;
- explicit error з вимогою виконати generation і закомітити результат.

Це принципово відрізняється від старого порядку `generate → generate:check`, де generator міг спочатку виправити stale file, після чого check урочисто підтверджував власний результат. Людство любить такі перевірки, де екзаменатор спершу сам заповнює тест.

## CI pipeline

`.github/workflows/docs.yml`:

1. checkout поточного `main` commit;
2. setup Node 22 + PHP 8.2;
3. `npm run docs:generate`;
4. committed generated-reference drift gate;
5. `npm run docs:generate:check`;
6. `npm run docs:check`;
7. `npm run docs:build`;
8. upload `public/docs` artifact;
9. push у `main` може deploy-ити `/docs` на AWS dev.

Workflow також має запускатися при змінах у code/manifests/contracts, які впливають на generated reference або канонічні документаційні контракти.

## Семантика помилки

Build не готовий, якщо:

- generator падає;
- committed generated reference дрейфує від current checkout;
- generated byte-for-byte check не проходить;
- internal links/frontmatter/contracts невалідні;
- Kernel/module facts не узгоджені;
- Process Registry topology/ownership/capabilities/runtime mappings невалідні;
- language/audience gates не проходять для свого корпусу;
- VitePress build падає.

GitHub Environment `AWS TN2026` окремо має дозволяти deployment із `main`; це repository-external protection rule.

## Правило зміни генератора

Якщо потрібно локалізувати або змінити generated reference, змінюйте generator/template/structured authority, а не результат у `docs/12-reference` вручну. Інакше наступна generation чесно поверне все назад, і буде права.
