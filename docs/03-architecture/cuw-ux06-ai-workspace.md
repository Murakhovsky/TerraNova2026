# CUW-C / UX-06 / #521 — робочий простір AI

Базова версія: `10fc649df6aafdca432ec329ebd737f6a4abd1ec` (Wave 2, батьківська задача #518).
Норматив: COS Unified Workspace Master Spec §§11, 19, 20, 21. Це ізольована реалізація, а не приймання D3/D4/D5 чи LIVE Hermes.

## Повторне використання, адаптація та нові компоненти

| Компонент | Рішення |
| --- | --- |
| Shell, UIContext, AgentRunReadModel, UIActionResolver | Повторне використання без змін спільних Shell, DI та маршрутів |
| Панель AI | Розширення GET-маршруту параметром `view=workspace`; той самий серверний шаблон і стабільні ідентифікатори DOM/frame |
| Незалежний від Runtime адаптер | Новий тегований інтерфейс і типізований результат `AgentRuntimeInspection`; за неоднозначності вибір блокується; лише читання |
| Перший Hermes-адаптер | Сервіси власника Marketing: перевірка контексту Campaign, готовність, закріплені ревізії Creative/AdSet, нативний журнал |
| Подання пропозиції | Чинний захищений POST `/marketing/campaigns/{id}/analyst-plans`; CSRF, стабільний ключ ідемпотентності, перевірки ролі та модуля |
| Workflow та Action | Чинний Federation Plan, незалежне погодження Plan і Action, авторизований worker, нативний запис виконання та перевірка результату |
| Дії з результатів Agent | Чинні проєкції UIActionResolver; без кнопок, згенерованих з недовіреного JSON; посилання на справжній Control Center |
| Engineering agents | Окремі профіль, облікові дані та адміністрування; бізнес-інтерфейс не отримує доступ до цих інструментів |

Поточна канонічна модель читання має доступ на рівні організації, а не користувацькі ACL. Тому історія AI доступна лише manager/admin з ACCESS і MANAGE. Перевіряються організація, роль, тип та ID сутності й нативний ID AgentRun для Action. Невалідний явний контекст не розширюється до історії організації. Для колекції без визначеного типу сутності лише явна прив'язка Marketing Campaign дозволяє контекст сутності. Непідтримувані контексти Runtime залишаються доступними лише для читання. Відсутність адаптера не надає дозволу викликати іншого провайдера.

## Перший сценарій R4

1. Відкрити глобальну панель AI та обрати AI Workspace.
2. Обрати Marketing Campaigns та кампанію своєї організації.
3. Перевірити готовність, ліміт віддалених інструментів (нуль), добовий ліміт запусків, бюджет і тайм-аут HTTP.
4. Якщо власник дозволяє створення Plan і профіль має операторський токен-контракт, обрати закріплену Creative / необов'язкову AdSet та запропонувати аналіз. Форма фіксує хеш конфігурації. Це **не** виклик Runtime.
5. Продовжити у Goals: незалежне погодження Plan і окремо авторизована Action. Чинний worker володіє єдиним шляхом віддаленого виклику.
6. Переглянути нативний журнал Hermes, псевдоніми джерел, їх ревізії та ID відповіді провайдера. ID нативного запуску є віддаленою кореляцією. Поради потребують незалежного рішення власника.
7. Відкрити журнал власника для перевірки або відновлення невизначеного результату. У Goals переглянути незалежно підтверджену квитанцію Action і верифікований результат запуску, якщо наявні. Порада не дозволяє платну активацію.

Загальні запуски Agent відображають структурований результат, рекомендації, недовірені пропозиції дій, докази та справжні проєкції Action/Approval. Подія `cos:workspace-action` не має виробничого споживача у базовій версії; UI посилається на канонічну операційну поверхню замість удаваного виконання. Завершення життєвого циклу й ID відповіді провайдера не є незалежним доказом бізнес-результату.

## Обмеження та обробка збоїв

Чинний авторизований адаптер Marketing забезпечує повторну побудову контексту, конфігурацію організації та приймання ізоляції, нуль дозволених віддалених інструментів, обмежений розмір HTTP body, 45 секунд на HTTP-запит, добовий ліміт і консервативне резервування вартості в Kernel. Автоматичний повтор після невизначеного зовнішнього результату заборонений; нативний журнал підтримує незалежне відновлення, а не скасування витрат. Точний контроль квитанції токенів реалізовано окремо від непідтвердженого жорсткого ліміту провайдера. Віддалене скасування у синхронному адаптері недоступне. Налаштований профіль не означає LIVE; операторські вимоги й облікові дані залишаються обов'язковими.

### Точні межі токенів та квитанція

Профіль UX-06 вимагає опціональне для попередніх Marketing-профілів поле `token_budget` у чинному deployment-only `COS_MARKETING_HERMES_PROFILES_JSON`. Наприклад, для тестового профілю:

```json
{
  "max_prompt_tokens": 800,
  "max_completion_tokens": 400,
  "max_total_tokens": 1000,
  "control_evidence_ref": "fixture-token-cap"
}
```

Це приклад структури, а не рекомендація для live профілю. Цілі числа обмежені, сума не оцінюється за довжиною тексту. Операторська декларація входить у канонічний configuration hash; зміна ліміту або evidence reference вимагає нового погодження. Власник Plan відхиляє застарілий хеш або профіль без токен-контракту для форми UX-06. Попередній Marketing шлях має незмінену сумісність; для UX-06 він не є підтвердженням токен-бюджету.

Адаптер перевіряє точні `prompt_tokens`, `completion_tokens` та `total_tokens` від Hermes, потім власник незалежно перевіряє їх за зафіксованим контрактом перед записом advice. Показники на межі приймаються; відсутність, неціле значення, нуль, перевищення на один токен, неузгоджена сума — відхиляються. У разі невідомого зовнішнього результату зберігається `UNCERTAIN`, витрачений резерв не повертається, автоматичний повтор заборонений. Нативна квитанція містить лише очищені лічильники, межі та `source=HERMES_REPORTED`, `hard_cap_verified=false`. Не є доказом жорсткого припинення генерації, фактичної оплати чи незалежного обліку токенів.

### Контроль зупинки та операторська перевірка

Офіційний [Hermes API Server](https://hermes-agent.nousresearch.com/docs/user-guide/features/api-server) описує `usage` у Chat Completions та окремий Runs API з `run_stop`. Документація не обіцяє сукупний жорсткий токен-ліміт для існуючого Chat Completions запиту. Поточна Marketing інтеграція використовує синхронний Chat Completions, а ID відповіді не є ID активного Runs API запуску. Тому не додаємо довільний POST stop, не підміняємо віддалене скасування локальним рішенням.

Команда `cos:marketing:hermes-preflight <organization> --probe --run-controls` читає лише авторизовані `/v1/toolsets` та `/v1/capabilities` у виділеному профілі; суворо перевіряє булеві можливості `run_submission`, `run_status`, `run_stop`. Позитивне оголошення не дозволяє виконання, не вмикає кнопку stop, не доводить ізоляцію або cap. Перед запуском можна відхилити незатверджену канонічну Approval у Control Center. Для невизначеного запуску доступне чинне незалежне відновлення з підтвердженням зупинки локальної та віддаленої роботи. Майбутній асинхронний адаптер потребує узгодженої прив'язки remote run ID до durable receipt, окремого канонічного control contract, перевірки fake/provider версії та operator acceptance.

Адаптер спочатку перевіряє активний модуль і належність сутності організації. Неуспішна перевірка приховує історію. Після підтвердження контексту готовність Runtime, планування та журнал читаються незалежно. Збій будь-якого з цих джерел блокує нове делегування, але не приховує доступні докази. Невідомий стан журналу не відображається як порожній журнал. Ручна робота та Control Center залишаються доступними.

Немає другого сховища запусків, погоджень чи результатів, прямого виконання з браузера, динамічної видачі інструментів/секретів, довіреного HTML або змін Kernel.

## Критерії приймання та перевірка

| AC | Покриття змін | Залишкова перевірка |
| --- | --- | --- |
| AC-04 / AC-09 | Захищена форма Plan і посилання на канонічні операції; структурована пропозиція відокремлена від виконуваної Action | Справжнє канонічне погодження в браузері |
| AC-10 | Відсутність адаптера, збої джерел та невідомі результати не спричиняють віддаленого виклику | Перевірка live збою Runtime |
| AC-11 | Негативні перевірки ролі, дозволів, організації, Workspace та сутності; читання кампанії власника | E2E ролей та організацій у зведеній версії |
| AC-16 | Кореляція й нативний журнал; посилання на канонічну перевірку результату | Незалежно підтверджена Action у staging |
| AC-12 / AC-13 | Серверне відображення, підписані поля, фокус/клавіатура, адаптивне перенесення | Знімки desktop/mobile і перевірка доступності |

Точки запуску автоматизованої перевірки:

- `php tests/architecture/cos_unified_workspace_ux06_contract.php`
- `php tests/unit/cos_unified_ai_workspace.php`
- Чинний Runtime-тест: `tests/integration/marketing_analyst_approved_goal_e2e_mysql.php` (ізольований провайдер, не LIVE) додатково перевіряє адаптер UX-06, належність контексту, недоступність Runtime/журналу, хеш токен-контракту, нативний доказ і відсутність повторного зовнішнього виклику.
- `tests/integration/marketing_m2_planning_mysql.php` — точні межі, перевищення на 1, некоректна/відсутня квитанція, тайм-аут, стійкий стан UNCERTAIN і нуль повторів на ізольованому transport fixture.
- Чинна команда `cos:web:ai-ui:smoke` (синтетичний запуск і справжня проєкція Action).
- `node tests/browser/ux06_ai_workspace.mjs` — окреме приймання лише для читання. Потрібні `UX06_E2E_FIXTURE_SAFE=1`, `UX06_E2E_BASE_URL=http://127.0.0.1:8081`, `UX06_E2E_EMAIL`, `UX06_E2E_PASSWORD`, `UX06_E2E_RESTRICTED_EMAIL`, `UX06_E2E_RESTRICTED_PASSWORD`, `UX06_E2E_CAMPAIGN_ID` та `UX06_E2E_FOREIGN_CAMPAIGN_ID` із двох ізольованих організацій. Звіти axe і знімки desktop/mobile зберігаються в `tmp/ux06-ai-workspace`. Для інтегратора додано `tests/browser/run_ux06_ai_workspace_fixture.sh` — самодостатня підготовка двох випадкових ізольованих tenant fixtures у чинному disposable CI Compose (без профілю Hermes). Немає змін загального workflow. Запропонований крок інтеграції після наявних browser jobs:

```yaml
- name: UX-06 isolated AI Workspace browser acceptance
  env:
    UX06_E2E_BASE_URL: http://127.0.0.1:8081
    UX06_E2E_FIXTURE_SAFE: '1'
  run: bash tests/browser/run_ux06_ai_workspace_fixture.sh
```

Окремим кроком завантажити артефакти `tmp/ux06-ai-workspace`; зафіксувати run ID, axe та знімки. Цей крок координує інтегратор #518; сценарій навмисне не допускає запуску seed проти production.

Локальне середовище не містить PHP, Composer або Docker; ці перевірки не запускалися локально. Необхідні CI і Runtime-приймання гілки та перевірка зведеної версії. Жорсткий ліміт токенів на боці провайдера, віддалене скасування через авторизований асинхронний контракт, загальне міждоменне делегування й незалежна LIVE-квитанція ще відкриті. PR не додає виробничого розгортання, віддаленого виклику чи активації.

Відкат: скасувати цей ізольований PR; міграцій схеми немає. Чинні Marketing, Control Center, Goals і маршрут панелі AI зберігаються.
