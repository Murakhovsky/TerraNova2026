# Visualization V0.5 — Process Runtime Evidence

Visualization V0.5 does not add a second Mermaid system. DOC V0.12–V0.14 already provide VitePress Mermaid rendering, Process Registry, ownership projections and generated-reference discipline. V0.5 closes the missing semantic link: **what proves that a process mapping exists in the current COS implementation?**

## Goal

Canonical chain:

```text
Business Process Registry
        ↓
Runtime mappings
        ↓
Runtime Evidence Catalogue
        ↓
Derived verification
        ↓
Business Process Reference / Mermaid views
```

Mermaid remains presentation. Generated Markdown remains presentation. Neither is allowed to verify the other.

## Two axes

V0.5 separates two concepts that were previously mixed in one enum.

```text
Business state                 Verification
-------------                  ------------
as-is                          documented
to-be                          source-verified
                               runtime-verified
```

`as-is` / `to-be` is authored business meaning.

Verification is derived and cannot be authored in a process definition.

## Evidence strengths

Current machine-readable evidence catalogue is generated by:

```text
docs/.vitepress/generate-runtime-evidence.php
```

It reads current checkout authorities directly.

| Mapping | Canonical authority | Strength |
| --- | --- | --- |
| `use_case` | registered Domain `Application/UseCase/*.php` | source |
| `command` | registered Domain `Application/DTO/*Command.php` | source |
| `source` | exact path + optional symbol | source |
| `event` | explicit Domain event catalogue | runtime |
| `contract` | module `cross_domain_contracts` | runtime |

`process-runtime-evidence.mjs` is the shared resolver used by process checks and generated Business Process reference.

## Verification algorithm

For each critical process step:

```text
no resolvable evidence
        ↓
DOCUMENTED

all critical steps have source evidence
        ↓
SOURCE-VERIFIED

all critical steps have runtime-strength evidence
        ↓
RUNTIME-VERIFIED
```

The strongest status only applies when **every critical step** satisfies the level.

`RUNTIME-VERIFIED` in V0.5 means structurally verified against canonical runtime/architecture registries. It does not mean an observed end-to-end production execution occurred. Execution traces belong to a later runtime-observability model.

## Relationship to Architecture Graph

Visualization V0.4.2 introduced first-class cross-domain contracts:

```text
Consumer Domain
   │ requires_contract
   ▼
 Contract
   ▲ provides_contract
   │
Provider Domain
```

V0.5 makes those declarations usable as process evidence. A future cross-domain process step can reference the same contract FQCN already used by Architecture Explorer instead of creating a second dependency vocabulary in documentation.

This preserves the invariant:

```text
Architecture truth ───────┐
                          ├─→ Process evidence → Documentation
Process truth ────────────┘
```

## Process Registry schema v3

Schema v3 changes the contract:

- `state` accepts only `as-is` / `to-be`;
- authored `verification` is forbidden;
- runtime mappings resolve against current checkout evidence, not generated Markdown;
- every declared mapping must resolve;
- source/runtime coverage is calculated independently.

Current Sales, Property and Diagnostic process definitions are migrated to v3.

## Deliberate limits

V0.5 does **not** infer `sequenceDiagram` from generic process steps. A sequence view requires participants, messages, call direction and interaction semantics.

V0.5 does **not** infer `stateDiagram` from steps whose `kind` happens to be `state`. Entity lifecycle needs canonical state-machine semantics.

Those can become later projections once the model contains the necessary facts. Fabricating them now would produce convincing diagrams with imaginary semantics, which is precisely what this EPIC is trying to stop.

## Gates

`docs:check` now verifies process mappings through the current-checkout evidence resolver.

Visualization CI verifies that:

- Process Registry is schema v3;
- business state and verification are separate;
- generated Markdown is not used as runtime evidence;
- canonical event and cross-domain contract evidence is available;
- all current process definitions pass evidence resolution.

## Result

After V0.5:

```text
Cytoscape
  = what COS consists of

Process Registry + Mermaid
  = how work moves

Runtime Evidence
  = how strongly those process claims are supported by current COS
```

That turns Visualization + Documentation into one inspectable operational model instead of two collections of diagrams that merely happen to use the same nouns.
